# V3 领域世界模式与用户剧本：完整设计方案

状态：设计稿，待评审。取代 `docs/v3-user-script-design.md`，并吸收其中的内容。

## 0. 摘要

V3 现在是"一题一个小环境"：每个任务有自己的几张小表、1–4 个工具和一份只含相关规则的政策。真实业务不是这样的：
agent 面对的是一个**持续存在的系统**，有十几个工具、海量数据和一本完整的政策手册，每个客户只涉及其中一小部分；
客户本身也不总是配合的，会给出备选方案、讨价还价、记不清信息、中途改主意。

本方案为 V3 增加**领域世界模式**：每个领域构建一次大环境，在上面批量出题；每道题配一个**用户剧本**
（一棵确定的决策树，加一段自由演出的说明）。现有的一题一环境模式保留，两种模式并存。
奖励仍然完全确定，可信度仍然靠独立实现的差分认证来保证。

## 1. 目标与原则

### 目标

1. 训练数据接近真实业务：大环境、多工具、长政策、真实日期、长对话、复杂用户。
2. 奖励确定且可信：每个任务的期望结果由独立实现交叉验证。
3. 规模化成本更低：codex 只在构建领域世界时出手，出题由便宜的模型完成。

### 原则

| 原则 | 含义 |
|---|---|
| 平台通用 | 平台能力只能来自真实业务的普遍需求；不出现任何 benchmark 的工具名、数据结构或政策措辞 |
| 配置与平台分离 | 领域选择、任务比例属于实验配置；平台默认仍从知识图谱采样多样领域 |
| 决定结构化、说法自由 | 影响结果的用户决定写成结构化的决策树，由平台执行；措辞、语气、节奏由模拟器自由演出 |
| 独立实现、差分认证 | 环境、oracle、标准动作由不同会话分别产出，互相验证 |
| 两种模式并存 | 一题一环境模式继续用于独立任务（直接计算、单次查询、主观建议） |

**能力准入准则**：一项能力要加进平台，必须在真实业务中普遍存在，并且对评测 benchmark 以外的场景也有用。
例如"双方都要操作设备"只对应少数领域，本期不做。

## 2. 核心概念

```
领域世界 World（每个领域构建一次）
├─ schema           实体与关系（客户、账户、订单、预订、支付方式、商品或服务……）
├─ data generator   确定性的数据生成器（带种子），生成几百到几千条记录，包含边界情况
├─ clock            真实日期时间锚点（如 "2026-03-14 10:30, UTC+8"），规则按真实日期计算
├─ spec             完整的内部规格：所有业务流程的规则（判分依据）
├─ agent_policy     由 spec 改写的客服手册（agent 只看这份），并通过覆盖检查
├─ tools            12–20 个工具：身份核实查询、各类查询、写操作（参数可以是嵌套结构）、转人工
└─ oracle           领域级 oracle：给定初始数据、用户事实、决策树和时间，计算任意任务的期望最终状态与答案

任务 Task（每个世界上批量生成）
├─ target           涉及的客户和记录（从世界数据中选取，必要时做少量定制修改）
├─ user_facts       只有用户知道的信息（身份信息、编号、偏好）
├─ decision_tree    用户的决定（结构化，由平台执行，oracle 也读取）
├─ script           自由演出的说明：诉求顺序、性格、坚持轮数、何时改口、记不清什么、先说错什么
├─ scene + opening  用户场景与开场白（沿用两阶段写法）
├─ gold_actions     每个决策分支各一组标准动作序列（由出题模型写，用于认证）
└─ expected         由领域 oracle 计算（不由出题模型写）
```

## 3. 用户剧本

### 3.1 决策树（结构化，决定结果）

决策树描述用户在每个决策点怎么选，条件只能引用**可客观判断的事实**：agent 提议的内容、当前数据库状态、用户事实。
用一种小型表达式语言写成 JSON，由平台解释执行，oracle 也读取同一份决策树来计算期望结果，不写成代码，便于审计。

```json
{"node": "proposal",
 "match": {"tool": "exchange_items", "args.new_item.switch": "clicky"},
 "decide": {"if": {"db": "product_variant_available", "args": {"switch": "clicky", "backlight": "rgb"}},
            "then": "approve", "else": "reject"}}
```

覆盖的决策类型有五种：同意或拒绝某次写操作；在多个方案中选择（按偏好顺序和可行性）；被拒后接受、继续坚持还是要求转人工；
听到费用或条件后改变意图；多诉求时决定是否继续办下一件。

### 3.2 剧本要素与比例（每个任务 1–3 种，另加性格）

| 要素 | 用户的表现 | 认证保证 | 比例 |
|---|---|---|---|
| 备选方案 | 要 A，A 不行就要 B | 数据里首选不可行；每个分支都有标准动作序列 | 40% |
| 坚持不合规诉求 | 先要政策不允许的结果，被拒后坚持 n 轮，再接受或要求转人工 | 期望结果是"不执行"或"转人工"；env 按规则拒绝违规写操作 | 30% |
| 多诉求 | 一次通话 2–3 件事，可以开头就说，也可以办完一件再提 | 期望结果覆盖全部诉求 | 30% |
| 记不清 | 不记得订单号或邮箱，能提供替代信息 | 运行时对这些事实返回"不记得"；世界里有替代查询工具 | 20% |
| 含糊需求 | "改一下那个订单"，而名下有多个订单 | 期望结果针对用户心里那一个；标准动作里包含先问清楚 | 20% |
| 先给错信息 | 先报错的编号，查不到后改正 | 运行时第一次返回错误值 | 15% |
| 中途改主意 | 听到费用后改成取消 | 由决策树表达 | 15% |
| 超出范围 / 转人工 | 提出政策之外的要求，或主动要求转人工 | 政策写明转人工的条件；转人工工具记录状态 | 10% |
| 性格 | 着急、啰嗦、话少、注重细节、不太懂行、非母语表达 | 不影响判分 | 每个任务都有 |

### 3.3 用户模拟器

模拟器读取剧本的说明部分，以及平台告诉它的决定结论（同意或不同意、选了哪个、是否坚持），用自然语言演出。
结束信号有三种：`[END]`（办完或不想继续），`[TRANSFER]`（要求转人工），`[OUT-OF-SCOPE]`（剧本覆盖不到的情况）。
坚持的轮数由平台计数，到了约定轮数就告诉模拟器"现在接受"或"现在要求转人工"，不依赖大模型自己数。

## 4. 生成流水线

### 4.1 世界构建（每个领域一次，使用 codex）

| 步骤 | 产出 | 由谁完成 |
|---|---|---|
| W1 领域 | 领域名称与说明（知识图谱采样，或配置文件指定） | 现有流程 |
| W2 世界规格 | schema、业务流程清单（8–15 个）、完整 spec、工具清单、时间锚点 | codex 规格会话 |
| W3 数据生成器 | 确定性生成器，产出几百到几千条记录，包含边界情况和干扰项 | codex 数据会话 |
| W4a 环境 | 全部工具的实现 | codex 作者会话 |
| W4b oracle | 领域级 oracle（看不到环境实现） | codex oracle 会话 |
| W5 政策 | 对外政策改写与覆盖检查（沿用现有流程） | deepseek |

### 4.2 世界认证

1. **静态检查**：工具定义、参数类型、不得出现通用读表工具、身份核实流程完备。
2. **流程探针**：codex 规格会话为每个业务流程给出 3–5 个探针场景（典型、边界、拒绝），env 执行标准动作，
   与 oracle 的期望结果做差分比对，有分歧时按 spec 原文仲裁（沿用现有仲裁机制）。
3. **换种子复验**：用不同的种子重新生成数据，探针差分依然成立（防止实现依赖特定数据）。

世界认证通过后，才在它上面出题。

### 4.3 出题（每个世界批量生成，使用便宜的模型）

| 步骤 | 内容 |
|---|---|
| T1 选题 | 按配额抽取业务流程和剧本要素；从世界数据中查询合适的目标客户和记录（出题模型通过只读查询工具访问数据） |
| T2 定制 | 必要时对目标记录做少量修改，制造触发条件（比如让首选商品缺货） |
| T3 剧本 | 写 user_facts、决策树、剧本说明、用户场景 |
| T4 标准动作 | 为每个决策分支写一组标准动作序列 |
| T5 开场白 | 沿用两阶段写法：开场白写手只看场景和性格 |

### 4.4 任务认证（每道题）

1. **一致性检查**：决策树只引用存在的事实和数据；剧本要素齐全；每个分支都有标准动作。
2. **差分**：在 env 中重放每个分支的标准动作（平台按决策树发放授权），得到的最终状态必须等于 oracle 对该分支的期望结果。
3. **反例**：什么都不做、违规写入、用旧数据作答，都必须拿不到分（沿用现有的反例 gate）。
4. **难度下限**：标准动作的工具调用次数达到下限（按任务形态设定）。
5. **抽取探针**：答案能从客服说法里完整读回（沿用现有探针）。
6. **policy gate**：deepseek 在自由对话、复杂剧本下至少解出 1/4。
7. **剧本执行诊断**（不作门槛）：抽样检查模拟器是否按剧本演出（坚持轮数、备选顺序、改口时机）。

## 5. 运行时

| 方面 | 设计 |
|---|---|
| 数据 | 世界的数据库在内存中加载一次，每个 episode 用写时复制的快照；任务的定制修改叠加在快照上 |
| 时间 | system 中给出真实日期时间；规则按真实日期计算 |
| 授权 | `approval_key` 推广为决策树解释器：输入提议、当前数据库和用户事实，输出决定 |
| 记不清 / 说错 | 运行时按剧本处理 `ask`：`forgotten` 返回不记得，`wrong_first` 第一次返回错误值；自由对话下模拟器同样遵守 |
| 转人工 | 作为一次写操作，记录状态，episode 结束 |
| 判分 | 不变：最终状态，加上答案（记录的或从话里抽取的）；主观任务用 rubric |
| agent 看到的内容 | 完整的对外政策、12–20 个工具（名字随机化不变）、开场白 |

## 6. 训练与评测

- **训练接入**：tasks.json 增加 `(world, task)` 类型的条目；rl 适配器加载世界包和任务；两种模式可以混合训练。
- **训练参数**：步数上限调到 40–60，上下文 24–32k，对齐真实对话长度。
- **评测（同时用来检查过拟合）**：
  1. τ²-bench（airline、retail）；
  2. V3 留出领域世界（领域完全没见过）；
  3. BFCL 多轮；
  4. 再选一个风格不同的 benchmark（如 VITA-Bench）。

  如果只有 τ²-bench 提升、其余不动，视为过拟合。
- **对比实验**：C_task（现有的一题一环境训练池）、C_world（领域世界）、C_mix（两者混合），回答"领域世界是否更有效、是否泛化"。

## 7. 与现有代码的关系

| 模块 | 改动 |
|---|---|
| core/spec | 增加 world 与 task 两种请求格式；保留现有格式 |
| runtime | 世界快照、真实时钟、ask 的 forgotten / wrong_first、转人工 |
| serving/server、user_sim、agent_view | 决策树解释器、剧本演出、三种结束信号、长政策与多工具 |
| authoring | 世界规格、数据生成器、领域 oracle、出题会话的提示与检查 |
| certify/gates | 世界认证（流程探针、换种子复验）与任务认证（分支差分） |
| production/run | `run --mode world`：世界构建、出题、认证、镜像、policy gate、tasks.json |
| rl 适配器 | 加载世界加任务 |

一题一环境模式的代码路径保持不变，现有沙箱继续可用（运行时变化后重签一次）。

## 8. 里程碑

| 阶段 | 内容 | 预计 |
|---|---|---|
| M1 剧本（一题一环境模式内） | 决策树解释器、剧本字段、forgotten / wrong_first、模拟器演出、转人工；30 题试点 | 1 天 |
| M2 世界构建与认证 | 世界规格、数据生成器、领域 oracle、流程探针、换种子复验；构建 3 个试点世界 | 1–1.5 天 |
| M3 出题与任务认证 | 出题会话、分支标准动作、分支差分、难度下限；每个试点世界出 30 题 | 1 天 |
| M4 训练接入与实验 | rl 适配、训练参数；C_world 和 C_mix 训练，多 benchmark 评测 | 2–3 天（以机器时间为主） |

M1 可以单独交付，现有的一题一环境任务立刻就能用上复杂剧本。

## 9. 风险

| 风险 | 对策 |
|---|---|
| 世界环境大，出错的地方多，一个 bug 影响整个领域的所有题 | 流程探针、换种子复验、每道题的分支差分三道防线；世界认证不过就不出题 |
| 出题模型写的标准动作有误 | 必须与 oracle 的期望结果一致才算通过，否则淘汰该题 |
| 决策树表达能力不够 | 第一版覆盖五类决策；遇到表达不了的情况，记录下来后扩展，不退回到让大模型自由决定 |
| 长政策、多工具超出 0.6B 的能力 | 按难度分级（工具数、政策长度、剧本要素数），做课程式训练 |
| 过拟合 benchmark | 第 1 节的准入准则，加第 6 节的多 benchmark 评测 |
| 模拟器不按剧本演出 | 坚持轮数等关键节点由平台计数并提示；剧本执行诊断持续监控 |
