# 循环工程实验

主入口 `scripts/run_pipeline.sh` 默认执行单轮 5 个 Code Agent 样本。`scripts/loop_experiment.py` 负责可恢复调度，`scripts/run_sandbox_build_loop.py` 保留为兼容 CLI。默认不复用历史高分，构建与独立审查模型固定为 `gpt-6-luna`。
新任务沿多跳 Scene 图谱路径生成；实验以独立 seed 采样任务，并检查留出集任务与开发集是否重复。

较大规模的生产认证实验可显式选择每轮生成 10 个新任务，固定使用
`direct_response=20%`、`simple_agentic=30%`、`multi_step_agentic=50%`。
实验分为两个阶段。开发阶段连续两轮达到任务良品率、条件构建良品率、端到端良品率、
分路由下限和合格样本均分后，自动进入生产准备留出集：

```bash
uv run python scripts/run_sandbox_build_loop.py \
  --generate-count 10 --max-rounds 0 --consecutive-rounds 2 \
  --validation live --build-mode clean \
  --sandbox-runtime docker \
  --experiment-seed 20260925 \
  --target-task-yield 0.85 --target-build-yield 0.80 \
  --target-end-to-end-rate 0.70 --target-qualified-mean 8.5 \
  --target-category-rate 0.60 \
  --output output/loop_experiment_v1 --hypothesis baseline
```

`--max-rounds 0` 是默认值，表示开发阶段没有轮数上限；仍受累计活跃时间预算和人工暂停控制。
默认 `--certification-profile production` 连续执行 3 个独立批次，每批使用 30 个留出请求并要求
形成 30 个全新任务；每个合格沙箱执行至少 10 次 rollout。各批次采用独立 seed、从零构建，
内容和 seed 不得与开发轮或其他留出批次
重复；数字、标点或轻微措辞改写形成的近重复任务家族同样不得跨越开发集和任何留出批次。
完成后由 `scripts/certify_training_materials.py` 根据置信区间、类别覆盖、重复率、跨分区家族隔离、运行时隔离、
奖励反事实和轨迹完整性生成 `production_readiness.json`。只有停止原因
`production_prepared_for_agentic_rl` 表示生产级训练素材准备认证通过。
30 个任务是单批样本规模，不降低奖励误判的置信区间门禁。默认 3 批总计至多
90 个独立沙箱；即使奖励假阳性为 0，其 Wilson 95% 上界也约为 4.1%，
无法满足 0.5% 的生产门禁。此设置可用于留出诊断，但默认规模不能取得
生产准备认证；若保持此误判门槛，需增加独立批次及合格沙箱总数。

需要快速验证候选实现时，可显式使用
`--certification-profile pilot --holdout-count 30 --holdout-rollout-episodes 3 --holdout-end-to-end-rate 0.70`。
Pilot 通过只表示可以进入更大规模认证，
不能表示生产准备完成。Pilot 只执行一个批次；生产认证的三个批次均为一次性留出集，失败后保留证据
并退出，不能回流调参后继续冒充留出集。

固定回归集可使用 `--task-ids 45,78,92,175`，不能与 `--generate-count` 混用。
`--build-mode repair` 允许固定任务继承上轮扩展实现，不复制 SQLite 状态及验收报告；其结果表示修复能力，不表示从零构建能力。新任务始终不继承旧任务实现。

## 配置和恢复

- `--threshold` 默认 8，统一采用大于等于；production 模式不允许低于 8。该值会进入冻结实验配置，
  并与 canonical 认证策略及其摘要绑定；不能通过 CLI、认证 API 或重写报告降低其他生产门槛。
  任务静态评分也是前置筛选，失败任务仍计入总请求数。
- `--validation offline` 只执行离线门禁，不能证明真实训练质量；默认 `live` 会追加真实模型 rollout。
- `--certification-profile production` 强制 `--sandbox-runtime docker`，每个候选环境必须实际构建内容寻址
  镜像并通过安全容器 smoke test；不能用 `none` 生成生产认证。pilot 可显式设置
  `--sandbox-runtime none`，但其结果仍只表示候选流程验证。并发 worker 使用互不相同的本地镜像 tag；
  smoke evidence 写入后立即移除临时镜像，避免大规模留出集发生 tag 串样或耗尽 Docker 存储。
  基础镜像可复用本机缓存，但必须具有匹配仓库和平台的内容摘要；Docker 构建或 smoke test 失败会保留失败状态。
- `--rollout-episodes 3 --rollout-steps 20` 控制开发阶段每个沙箱的轨迹次数和步数。开发阶段默认只要求至少
  一条成功证据；`--rollout-min-success-rate` 可提高该门槛。生产留出集默认使用 10 次 episode 和
  `--holdout-rollout-success-rate 0.6666666666666666`。
- live 模式的最终 10 分由离线可执行证据占 9 分、真实 rollout 占 1 分组成；任何 live 硬失败仍直接取消训练资格，不能依靠离线高分抵消。
- 离线评分通过后、任何外部模型调用前，流水线先运行数据治理审计并生成 `data_governance.json`。
  缺少有效数据来源声明、发现凭证或无法确定 Agent/User/Judge provider 时停止该样本；疑似 PII 会被记录。
  当前只接受任务流水线生成的合成业务数据。该技术审计不替代实际外部端点所需的组织授权。
- live rollout 通过后会以 `SANDBOX_EVALUATOR_MOCK=0` 执行奖励反事实校准，写入
  `agentic_training_value_live.json`。真实 evaluator 的成功轨迹、失败轨迹、无工具、错参数、跳步、乱序和
  噪声轨迹不满足奖励分离时，样本仍不合格；计算／估算任务还会将成功回答中的数字改错后重测。
  离线 mock 报告不能替代该证据。
- production profile 保留完成冒烟验证的本地镜像直到 live rollout 结束；Agent 驱动器在宿主侧运行，
  但所有工具、状态持久化、User Simulator 和奖励调用都通过随机 loopback 端口进入实际容器。容器停止后
  才删除镜像。轨迹中的 image ID 与构建 provenance 不一致，或退回进程内 app，都会取消生产资格。
- live rollout 与奖励校准之间执行 policy-visible 隐私审计，写入 `trajectory_privacy.json`。User
  Simulator 内部 outcome/FSM 标签只进入 trainer-only evidence，Agent 可见 `result` 只保留实际传给
  Agent 的 `user_query`；发现凭证或隐藏控制字段时停止样本，不能进入便携训练素材包。
- `--build-timeout`、`--generation-timeout`、`--score-timeout`、`--rollout-timeout` 分阶段限时，超时清理进程组。
- `--max-total-seconds` 默认 259200，只累计实验进程的活跃执行时间；正常暂停不消耗预算。`runtime_state.json` 保存累计活跃时间和运行状态。质量循环不再因“停滞”或固定 20 轮提前结束；显式设置正数 `--max-rounds` 才启用轮数预算。基础设施超时属于异常中止而非质量收敛。
- 同一个实验目录只允许一个运行进程；每个任务完成即原子保存。相同命令重启可恢复，不重复执行已经完成的任务；未完成构建使用新的 attempt 目录。中断的生成不会自动重新抽样；只有 manifest 标记 `completed` 且 `task_sha256` 与任务文件匹配的候选可进入构建，其余按生成基础设施失败计入分母。
- 代码、配置或固定输入变化时必须换实验目录，以免把不同版本的结果混为一谈。实验还会冻结 Python、
  OS/架构、项目直接依赖的已安装版本以及 `pyproject.toml`、`uv.lock` 摘要；这些执行环境信息发生漂移时
  同样拒绝恢复。快照不采集主机名、路径、环境变量或密钥。旧版 history 不能直接作为新实验续跑。

`experiment.json` 保存配置及代码/输入指纹；每个生成请求在模型调用前写入
`generation/task/task-N/sample_manifest.json`，记录 batch index、route、run seed、sample seed、可用环境能力和生成 provider。
每次 route attempt 还记录实际响应模型计数、finish reason、token usage 与 provider response ID 哈希；
不保存 prompt、响应正文、凭证或原始 response ID。manifest 也记录预留时间、生成耗时和
每次尝试耗时，用于计算逐样本从预留到构建结束的真实墙钟时间。生产认证会独立验证 provider、seed 和 attempt 链。
生成失败时保留目录并写入 `failure.json`，不会再删除失败样本的身份和归因证据。
`round-*/round_report.json` 保存任务状态；`history.json` 同时保存生成完成率、任务良品率、
条件构建良品率、端到端良品率、合格样本均分、分类型统计和停止原因。

开发阶段可从单个冻结实验的逐请求记录重算分路由良品率与失败码分布：

```bash
uv run python scripts/diagnostics/report_development_yield.py \
  output/loop_experiment_v1/history.json \
  --output output/loop_experiment_v1/development_yield.json
```

报告只用于开发诊断，不能代替生产认证。构建器在 `status.json.failed_phase` 保留最终失败门禁；
实验调度器据此区分业务构建、语义审查、运行时完整性、mutation 和 Docker 等失败。
Code Agent 遇到可识别的连接中断、限流或服务端暂时不可用时，保留工作目录并重试调用；
仍失败会写入 `failure_code=INFRA`，批次构建器默认再以 `--resume` 续建一次。
已完成模块通过检查点跳过，中断模块重新执行；中断的缺陷修复预约不消耗业务修复预算。
历史实验缺少 `failed_phase` 时仍保留原来的通用 `BUILD_BUSINESS` 归因，不根据日志猜测或改写旧证据。
任务评分与构建前检查共用必需 HTTP 端点清单；缺少 Trainer `/v1/state` 等端点时，
保留描述性质量分，但取消训练资格并以 `TASK_RUNTIME_INTERFACE` 在 Code Agent 启动前拒绝。
任务生成器在每次候选完成后先写出 `task.json`，运行同一构建前检查；任务质量、验收 fixture 或工具链 schema
不合格的候选进入该路由的剩余重采样次数，不发布为成功任务。构建前检查对成功轨迹中的 capture/`$ref`
执行保守的 schema 兼容性分析：若上游输出必含下游明确禁止的字段，以 `TASK_TOOL_CHAIN_SCHEMA` 拒绝，
避免 Code Agent 在不可变契约上反复修复。动态键对象的 `additionalProperties` schema 由外层契约检查和
共享运行时一致接受，并在调用时验证动态值类型。

## 模型默认值

Rollout Agent 按字段优先使用 `ROLLOUT_LLM_API_KEY`、`ROLLOUT_LLM_BASE_URL`、`ROLLOUT_LLM_MODEL`
和 `ROLLOUT_LLM_TIMEOUT_SECONDS`；缺失或空值回退到任务生成使用的对应 `LLM_*`。User Simulator 和
奖励 LLM 同样优先使用 `SANDBOX_LLM_*` 并逐字段回退到 `LLM_*`。显式配置某个字段不会覆盖其他字段，
三个角色的 provider 身份分别冻结和审计；缺少实际所需角色的模型或密钥时明确报错，不静默使用 mock。
正式认证的前置检查还要求 Rollout Agent 与 User/Judge 的 provider 主机和模型名称均不同，且签名私钥与受信公钥配对。

CLI 从项目 `.env` 加载环境变量；独立沙箱/容器应由启动器注入这些变量，不复制 `.env` 或密钥进入沙箱文件。离线模式仍强制 mock。
使用 Kimi K3 时可设 `KIMI_K3_REASONING_EFFORT=low`；实验配置记录该档位，并将其传入生成、Rollout Agent 和容器内的 User/Judge 请求。K3 请求不传 `thinking=false` 或低温度参数。

## Rollout 证据

Agent 只获得题面、公开工具及观测，使用 JSON 动作协议自主调用工具或回复用户；不读取成功答案、奖励规则和隐藏业务状态。User Simulator 使用真实 LLM，协议失败的 fallback 会单独标记并阻止 live 验证通过。

保存 transition schema v2：每一步包含完整公开模型输入、原始输出、解析动作、工具/User Simulator 结果、
前后观察、奖励、terminated/truncated 和调用用量；同时保留 HTTP trace 与 replay。轨迹绑定任务哈希、
沙箱可执行输入摘要、模型及 provider 摘要。检查无操作高奖励、重复奖励不稳定，以及 stateful 目标不满足
却得到高奖励。模型没有完成任务记录为缺少成功证据，不直接断言环境有错。

这里的“User Simulator 结果”对策略侧仅指公开 `user_query`；outcome category、transition ID、match
status 和 termination reasoning 属于 trainer-only metadata。便携 JSONL 采用字段白名单重新投影，不会
因为未来在内部 rollout 结构中增加调试字段而自动把它们泄漏给训练策略。

开发阶段的默认 live 门要求至少一条成功轨迹、全部轨迹无已检测环境问题且无 LLM fallback；
发布留出集将成功率门提高到至少 2/3，并要求轨迹池同时包含成功和失败样本。
报告将失败责任区分为 `agent`、`environment` 和 `infrastructure`；Agent 未完成任务不再自动归咎于沙箱实现。
它仍是有限成功证据，不是训练质量的完备证明；同模型担任 Agent/User/Judge 有相关性偏差。

循环工程的版本单位是“冻结源码的一次实验”，不是在同一源码上反复抽样。每个候选版本先使用相同
`--experiment-seed` 做配对回归，再用新 seed 测量分布外良品率。一次候选版本只修复一个可复用根因；
不允许在运行中的实验目录对应源码上继续修改。最终候选冻结后由调度器自动运行生产留出集，
每个新构建还必须通过 `task_lineage.json` 证明生成任务与沙箱内运行任务字节一致，且没有发生旧式绝对
manifest 路径迁移；否则以 `TASK_LINEAGE` 失败，在评分和 live rollout 前终止。
`history.json` 的最终停止原因只有 `production_prepared_for_agentic_rl` 才表示生产准备认证通过；
`holdout_target_met` 仅属于 pilot 门禁。

生产认证通过统计、真实性和不可变性门禁后，还必须成功导出并复验
`training_materials_bundle/`。该包使用相对路径和内容摘要，可直接迁移到后续 RL 数据转换/训练系统；
仅存在指向本机输出目录的清单不再足以触发生产准备停止原因。包验证器会从原始 rollout 重建
transition 投影并验证 episode/step/终止关系；它证明训练素材可摄取，不宣称已经执行 RL 训练。
Bundle v17 内置 `certification.json`、`dataset_card.json`、`experiment_contract.json` 和机器可读
`consumer_contract.json`；后者固定
transition JSON Schema、记录顺序、任务生成来源、环境重建入口以及 policy/trainer 可见性边界。数据集卡的构成统计、模型偏差、用途限制与
内部使用边界会同实际 transition 交叉验证，不能通过重新计算 manifest 哈希伪造更宽泛的认证结论。
每条 transition 还必须通过独立消费者记录校验；消息和 transition 都采用精确字段集合，不能夹带未声明的
trainer-only 元数据。
环境交付同时要求 `portable_build_context_ready`：平台规范化 `.dockerignore`，递归清点全部 Docker 重建
输入，并拒绝凭证文件、运行数据库、reviewer 日志、符号链接和未声明隐藏路径进入构建上下文。
导出的验收 rollout 会被机器标记为认证证据而非已认证的直接策略优化目标；生产准备认证覆盖环境的
新鲜 rollout 采集能力，不替代下游算法对轨迹用途的审批。
每次 Agent 与 User Simulator/Reward Judge 的外部响应还会保存实际返回模型的聚合 provenance 和响应 ID
哈希，避免仅凭请求时配置的模型别名声明运行身份；三类实际响应模型还必须落在实验启动前冻结的 allowlist 中。
生产 profile 还必须传入 `--bundle-signing-private-key` 与 `--bundle-trusted-public-key`（或在 `.env` 中设置
`ENVFACTORY_BUNDLE_SIGNING_PRIVATE_KEY`、`ENVFACTORY_BUNDLE_TRUSTED_PUBLIC_KEY`）。私钥应由组织密钥管理
系统保管且不得提交到仓库；实验清单只冻结公钥身份。未签名包和只携带自声明公钥的包均不能通过生产门禁。
正式实验获得输出锁后、启动任务前会写入 `production_preflight.json`，以非敏感方式检查 Codex、Docker daemon、
OpenSSL、模型/runtime 配置、签名密钥配对及工作区余量；默认至少需要 10 GiB，可通过
`ENVFACTORY_MIN_FREE_GIB` 提高。preflight 不向模型 provider 发请求，联网授权与可用性仍由运行方负责。
任务会在每个训练类别内按近重复任务家族确定性分层为 80% train、10% validation、10% test；同一家族及
一个任务的所有 episode/transition 共享同一 split。生产包要求每个类别覆盖三个 split，且任务家族不得
跨类别或跨 split，防止模板变体泄漏到下游评估集。

## 2026-09-27 开发诊断

两轮源码冻结的 30 请求开发批次分别保存在
`output/development_task_yield_20260927_frozen30/` 和
`output/development_task_yield_20260927_fix1_30/`。两轮均生成 21/30 个可构建任务，
Wilson 95% 下界约为 0.52，未达到 0.85 的开发目标。第一轮多步 Agentic 为 8/15；

直接回答为 6/6。两轮 seed 不同，不能把类别变化直接归因于代码改动。

第二轮 8 个生成成功，6 个通过构建、2 个在第三轮修复后仍因验收失败而终止。
两轮固定样本的端到端结果均为 6/10，验证模式均为 `offline_mock`，不含 live rollout。
具体样本、失败代码、模型、离线分数和 Docker 证据见各轮的 `task_yield_summary.json` 与
`build_probe_summary.json`。这些诊断结果不构成生产认证。

针对多步瓶颈的第三轮冻结实验保存在 `output/development_multi_step_20260927_fix2_15/`：

多步成功轨迹的参数修复发现重复工具调用会丢失逐次 fixture：旧实现以

记录时，A 调用缺参数会被错误补成 B。现在按业务调用位置取同位置基线；
仅对在基线中唯一出现的工具保留按名称回退。新增重复调用回归验证
A、B 分别补回各自标识，且原提案不被修改。任务生成 225 个测试通过。
这个修复提高生成轨迹的语义正确性，仍需新批次衡量良品率影响。

成功轨迹的工具参数预验收此前只检查必填参数，且对整数、数值和布尔 schema
未做类型判断；错误值可继续进入 TaskSpec 编译或沙箱构建。现在检查所有已
提供参数的类型，拒绝布尔冒充整数、字符串冒充数值、NaN/无穷大及超大到
无法表示为有限数值的值；支持可空类型，并保留可选空文本的原有语义。

从三个已有探索批次抽取 10 条成功任务的业务验收场景，以当前校验器重评均
通过。尚无新批次可量化生成良品率。

只读业务数据的结果奖励发现静态准入假阳性：把结果指标设为规则判断
“最终回答包含建议”并提供对应 `contains` 实现，旧任务评分仍为 10 分且
可准入，但该规则不核对私有业务记录。现要求只读数据的每个结果指标
要么使用从当前私有数据重算的 `numeric_targets`，要么使用带平台事实
核对准则、最终回答／工具结果／业务数据三类输入的语义 Judge。生成阶段
将 `business_state_rule`、`document_rule` 和 `trajectory_rule` 结果指标
转为后者，随后补齐事实核对输入。更新认证测试中的旧式夹具后，全量

可准入，另 6 条由原有事实核对门禁拒绝。生产级奖励误判率仍须真实
独立 Judge 与新留出批次验证。

进一步检查奖励执行顺序发现：同一语义 Judge 指标若又声明规则实现，
规则分数会先进入 `existing`，运行时跳过 Judge。任务评分现拒绝这种
同 ID 混合声明；只读数据的语义结果指标必须为 model-based/hybrid 且
不得有声明式实现，规则结果指标只允许 `numeric_targets`。回归覆盖

生产认证 66 个测试通过。

规则型数值结果的测试夹具改为与实际生成器一致的 `document_rule` 声明。
另外独立沙箱评分的契约门禁现在重跑当前任务文件评分并要求准入，避免

通过；旧沙箱失格符合新准入要求，尚不能据此推断新批次生产良品率。

状态任务的目标闭环检查发现空集合漏洞：无最终行断言、无变更工具时，

批次交叉核对。策略版本升至 1.2；全量回归 679 个测试、23 个子测试通过。

奖励误判置信区间改按沙箱聚类计算：同一沙箱的多个反事实有相关性，
不能当作独立样本扩大分母。逐案观测误判率和按沙箱计错的 95% Wilson
区间上界必须同时达标；无正例或负例的沙箱在区间中计错。策略版本升至
1.3；全量回归 680 个测试、23 个子测试通过。

任务生成阶段的临时 LLM 错误重试不再携带“上一轮输出结构错误”的修复提示：
429/502/503/504、服务繁忙、超时及不完整响应会按原请求重试并退避；
候选最终失败时归为 `INFRA`，避免把服务故障误计为任务语义缺陷。
全量回归维持 680 个测试、23 个子测试通过。

奖励反事实认证进一步对齐实际执行器：`goal_failure`、`no_tools` 和
`noise_selection` 必须完成并给出低奖励，HTTP 4xx 拒绝不再可作为这些
轨迹的通过证据；损坏参数、跳步及乱序仍允许明确客户端拒绝。此前认证器
会接受伪造的目标失败拒绝报告，而实际执行器本身要求拿到低奖励。
策略版本升至 1.4，全量回归 680 个测试、23 个子测试通过。

真实 rollout 的成功率认证补上逐 episode 交叉核对：从终止原因、初末奖励、
问题集合及业务目标行谓词复算 `agent_success`，并核对汇总成功率。之前仅
对已声明的成功标记计数，篡改标记及比例仍可能通过。针对终止奖励和
业务状态漂移的回归均通过；策略版本升至 1.5，全量回归 682 个测试、
23 个子测试通过。

rollout 轨迹校验进一步把 episode 的初始、逐步和最终奖励及初末业务状态
绑定到原始 HTTP 读取结果，拒绝缺失、额外读取或汇总字段漂移。对应正向
素材夹具已按实际执行器的读取顺序更新；策略版本升至 1.6，全量回归
683 个测试、23 个子测试通过。此项是验证器回归，不代表新的生产良品率。

沙箱构建状态 `status.json` 现保存 `started_at_epoch`、`elapsed_seconds` 和
`phase_timings`。每次进入准备、可构建性预检、模块开发、验收、缺陷修复、
独立审查、mutation、Docker 构建及离线评分等阶段均记录一次区间；重复阶段
保留为独立条目，失败也会关闭最后一个区间。重启一次构建会重置本次计时，
批量实验仍分别保存每个沙箱的状态文件。旧状态文件不具备这一计时证据，
历史耗时只能从产物时间戳粗估。任务准备阶段失败现在也会写入终态及
耗时，避免留下一直显示 `pending` 的样本。

episode 轨迹门禁继续把每个有效动作与原始 HTTP 请求对应：工具名、参数、
响应状态与结果，或最终回答、用户模拟器返回值，以及动作前后的观察，
均需按执行顺序一致。仅保留奖励读取而伪造动作或观察现在会被拒绝。
额外动作 HTTP 请求也不能进入通过轨迹。用真实 rollout 发射器构造直接回答
和单工具后回答两类 episode，均通过新 schema；篡改回答、观察或插入额外动作
均被拒。认证策略升至 1.7；全量回归 686 个测试、23 个子测试通过。
旧实验必须按新策略重新生成和认证。

按每批 30 个任务的要求，留出实验默认请求数、生产最低形成数、冻结配置
契约及认证策略已统一为 30；三个批次累计 episode 下限调整为 750。
轨迹同时要求 reset、工具清单和 replay 的原始 HTTP 骨架与 episode 一致。
回归证明 3×30 样本即使零奖励误判仍不能通过原有置信上界门禁，认证会
如实失败而不会把小样本当作生产级证据。全量回归 687 个测试、23 个
子测试通过；尚未运行新的实际留出批次。

开发汇总、诊断报告和认证报告现在增加 `post_score_survival_rate`：先通过
离线沙箱评分的样本中，最终也通过 live 流程的比例；同时记录分子、分母
和认证侧 Wilson 95% 下界。它用于回答“评分器放行后还有多少样本存活”，
但只是流水线内的条件通过率，不能代替独立标注的生产良品率。
纯离线实验或没有评分通过样本时，该比率为 `null`（尚不可测），不会把
缺少真实 rollout 的离线通过误写成存活，也不会显示成 0%。

## 2026-09-29 评分后存活与独立良品开发基线

本次 pilot 请求 10 个新任务，生成成功 9 个、失败 1 个。用这 9 个固定任务在
`output/baseline_survival_verified_20260929/` 从零构建、执行当前离线评分和
Docker 容器 live 验证；5 个在构建阶段失败，4 个离线评分通过，其中 2 个
最终通过 live 流程。**评分后存活率为 2/4（50%）**，Wilson 95% 下界约
15.0%。另两个评分放行样本分别因 Agent 3 次均未完成目标，以及私有业务数据
变化后旧答案仍获得奖励而失败。

对 2 个存活沙箱逐项复核任务目标、真实状态变化、奖励反事实和事实素材来源：
补货任务确实新增目标批次的 50 盒申请，确认为良品；粤剧知识任务把整部剧目
直接标为发声方法或个人唱腔的代表，未给出表演者、唱段或可靠来源，且回答将
“薛腔”表述为“平喉的进阶流派”，未通过独立事实溯源要求。**已确认的存活
沙箱良品率为 1/2（50%）**，Wilson 95% 下界约 9.5%。完整逐样本判定和
来源在 `baseline_review.json`，原始逐请求证据在 `history.json`，条件比率及
置信下界在 `development_yield.json`。这是小样本开发基线，不是生产认证结果。

测量中先后修复 Dockerfile 摘要固定发生在独立审查之后、live 入口模块导入
失败、容器 HTTP 客户端 30 秒超时短于真实评估调用这三处流程问题。最终基线
仅使用修复后的独立重建目录；原始生成批次和中断的诊断重建没有混入条件比率。

后续性能改动把与任务事实无关的用户画像固定为四种可轮换的结构化脚手架，
并从已验证业务表确定性渲染数据说明和噪声工具 fixture，减少逐任务模型调用。
构建完整验收成功后不再立即重复运行契约、运行时、outer conformance、mutation
及基线验收；独立离线评分仍重新执行这些检查。改动尚未跑新的冻结样本批次，
因此不能从历史耗时或测试通过推算新的 5 分钟达成率及良品率。

后续构建路由对零自定义节点沙箱的 `/v1/reward` 外层验证超时先做一次无模型
复验；重复超时标记为 `BUILD_RUNTIME_TIMEOUT`，转交共享运行时或任务契约排查，
不继续消耗任务 Code Agent 修复预算。生成中断恢复也只接纳 manifest 已标记
`completed` 且任务 SHA-256 匹配的候选；纯声明式工具与指标的验收契约改为
优先使用通过校验的确定性基线。历史 9 个生成任务的基线回放均通过结构检查，
其中 7 个满足免验收契约模型调用条件。以上仍是开发验证，不是新批次耗时或
良品率结果。

生成与构建现按已完成样本并行调度：只有 `sample_manifest.json` 标记 `completed`
且 `task.json` 摘要匹配后，构建才会启动；生成仍在运行时保留部分并发槽位给生成 worker。
开发诊断增加 `generation_seconds`、`generation_build_seconds` 与 `sample_latency_seconds`：
第二项从样本预留计至沙箱构建进程结束，用于核对 5 分钟目标；第三项计至后续验证结束。
诊断报告另列 `generation_build_seconds.final_qualified_within_300_seconds` 及其相对全部
请求的比率，同时要求在 5 分钟内完成构建并最终通过 live 门禁；最终合格样本若缺构建
时间戳，比率为 `null`，不把证据缺失误记为达标。
两者都统计 300 秒内完成的样本。旧批次缺少时间戳时该比率为 `null`。
生成模型的 HTTP 429/500/502/503/504 现在在同一候选内有限重试，避免暂时性故障
直接触发整条候选重采样。尚需新的冻结批次验证 5 分钟达成率与 Agentic 良品率。

获准的单样本真实生成烟测保存在 `output/perf_smoke_20260929_authorized/`：
Neo4j 抽取约 0.23 秒，生成在 13.43 秒退出；任务描述连续三次遗漏规划阶段选定的
“西安测绘研究所”锚点，前置门禁拒绝了候选，因此没有沙箱构建时间或新良品率。
当时 route repair 只要求“至少一个 Scene 关键词”，与校验器要求的**选定锚点**不一致。
现已把确切锚点写入首轮描述提示和定向修复提示，并附加独立 `required_anchor_term` 字段；
此修复通过本地测试，仍待下一个获准样本实测。
该失败样本的四次模型请求累计 13.004 秒，候选处理耗时 13.243 秒，模型等待占约
98.2%；这只定位该样本的生成瓶颈，不能外推到成功任务或构建阶段。开发诊断现汇总
`generation_recorded_llm_seconds` 与 `generation_unattributed_seconds`。后者包含本地处理、
未成功返回的模型请求和其他等待，不能直接当作本地计算耗时。

历史固定集的构建阶段计时显示，`defect_repair` 累计 3176.4 秒、`acceptance`
累计 2465.4 秒；mutation testing 累计 70.8 秒。这说明缩短突变验证只能节省一部分
验收时间，主要瓶颈仍是缺陷修复与整体验收。mutation runner 现保留通过的基线验收和
独立 HTTP 检查；每个突变一旦被业务验收明确杀死，就不再启动第二个运行时重复执行
外层 HTTP 检查。外层已通过的首次基线验收也可供 mutation runner 复用；runner 会
核对构建上下文摘要和通过报告，发现中途改动或证据缺失则自行重跑基线。突变结束后
仍执行一次干净基线以恢复证据。以上保持“任一验收层杀死突变即合格”的判定语义，
历史已通过的直接回答沙箱在两份本地副本上重放，原路径 0.90 秒、复用路径 0.78 秒，
两者均杀死 4 个适用突变；该单样本差值很小，不能作为主要性能收益或批次结论。
实际省时仍需新批次测量。历史失败样本中出现两个缺陷各修复 3 次仍失败的情况，因此增加样本级
修复预算；默认 4 次是开发阶段的资源上限，不代表已满足每样本 5 分钟目标。

零开发节点并不保证无需修复。历史样本 001 的声明式 `insert` 漏映射存储表的
`request_id`，共享数据层要求插入完整行，因而首次业务验收失败并消耗一轮修复。
任务生成现在对同名且未映射的公开参数确定性补全 `insert.values`；如果缺失列已无可用
工具参数，当前候选立即失败，不再对同一不可能成立的 spec 发起模型修复。状态型目标表
仍须满足声明式变更覆盖门禁。任务文件评分器以 0 分硬拒绝旧任务，构建前可构建性预检也报
`INSERT_ROW_INCOMPLETE`，避免缺陷进入沙箱验收。
用历史样本 001 当前任务文件重放预检，已从 `buildable=true` 改为拒绝并指出
`missing_columns=[request_id]`。这只证明该缺陷前移，不等于新任务样本的实际耗时或良品率。
声明式 insert/update/delete 在运行时会直接索引 `values`、`selector` 和 `changes` 的
参数。对应工具 schema 现必须将这些参数声明为必填；任务评分和可构建性预检分别
硬拒绝遗漏，避免成功轨迹恰好带齐参数、其他合法调用却在沙箱里抛出 KeyError。
历史 9 个任务没有新增此类拒绝，仍需新样本评估实际收益。
生成业务数据后，主外键和字段约束、任务关键词覆盖、stateful 初始状态现在先做确定性校验；
只有这些检查通过才调用独立 grounding 模型审查。确定性失败仍进入原有数据定向修复，
避免为已知无效的 rows 支付审查调用。完整本地回归通过；节省的调用数和耗时尚需新批次计量。
`direct_response` 的环境模式由训练路由固定为 `stateless`；生成器现在直接使用该脚手架，
不再调用模型规划一个随后必被覆盖的环境模式。此类任务没有业务工具，声明式业务工具
实现规格固定为空，也不再请求模型生成空 `specs`。其余训练路由仍按任务描述规划环境。
成功工具轨迹预演现也覆盖状态型任务中定制 handler 之前的声明式调用；用共享
`ManifestDataStore` 的内存状态执行 select、insert、update 和 delete，因此重复主键、
外键、字段类型及 CHECK 约束失败可在任务评分和可构建性预检时暴露。预演调用还使用
共享 `validate_json_schema` 检查解析后的工具参数，避免绕过真实运行时的必填、类型和
额外字段限制。定制 handler
之后的行为仍由沙箱验收验证。历史 9 个任务的离线评分重放没有新增拒绝；另有单测证明
重复主键写入会被预演拒绝，实际新任务良品率仍待批次测量。

直接回答任务若明确要求现实领域的代表作品、人物或历史实例，生成阶段和任务评分器现在
要求公开材料带有可追溯 URL；缺少来源会在构建前拒绝。历史粤剧唱腔样本 002 原来
任务评分 10 分，独立复核发现例证失实；用现有任务文件重放，新门禁返回 0 分并指出
缺少来源。此门禁只检查来源是否存在，不核验网页内容，也不覆盖所有事实性问题；
新批次仍需观察误拒和最终良品率。

单轮 5 请求试验暴露了评分口径不一致：任务 002 原评分 10/10，但独立审查发现工具契约要求
`status=active`，声明式查询既不筛选也不返回 `status`。任务评分现将这种不可验证的
工具前置条件作为硬门禁；同一任务文件重评为 0/10，避免进入构建。任务 001 原构建审查
将结果指标的 `terminal` 范围误解为 User Simulator 必须先完成用户确认；运行时契约中
该范围表示在 Agent 提交最终回答后由奖励端点评估，除非目标或指标明确要求用户确认。
澄清独立审查提示后，同一任务固定样本重跑通过了构建审查。任务分仍是构建前资格分，
最终交付需同时通过沙箱评分和 live 验证；不能用任务 10 分代表已交付良品。
原始 5 请求中生成交付 3 个，2 个因语义契约不合格被拒；生成耗时中位数 199.9 秒，
有记录的模型等待中位数 183.6 秒。3 个进入构建的样本，构建耗时中位数 134.6 秒；
3 次独立语义审查合计 294.6 秒。原始批次只有 1 个通过离线沙箱评分，其最终 live
结论因运行中修复构建上下文规则造成主进程版本不一致而未执行。上述批次不是同一代码版本
下的严格前后对照；固定样本重跑结果单独记录，不能并入原始单轮的良品率。
固定样本 001 在澄清审查语义后，构建约 83.1 秒并通过完整 live 验证，最终 10/10。
固定样本 002 的构建审查仍发现真实任务契约缺陷；新前置门禁已将其从 10/10 改判为
0/10。固定样本 004 构建约 198.3 秒、live rollout 通过，但真实奖励校准发现
`business_data_reward_sensitivity` 不成立，即私有业务数据变化后旧答案仍可得分，
因此最终不合格。其高离线分只表示离线验收通过，不能替代最终训练良品判定。

本轮样本 004 的可观察性修复多次让模型重写完整成功场景，返回约 10–15 KB 的残缺 JSON，
并触发嵌套重试；日志中该阶段 12 次请求累计约 128.1 秒，占该样本生成约 218.8 秒的
58.5%。生成器现只要求模型返回修复后的业务工具调用步骤；reset、最终回答、
reward 和断言由确定性代码沿用原场景。替换步骤后仍执行原有参数、依赖、可执行性与
可观察性校验。该改动已通过本地回归，但尚无获准的新生成批次，不能声称实测提速或
良品率提升。

固定样本 004 的 live 奖励校准中，私有商品记录改动后，旧答案在两次真实评估中分别得
0.3 和 1.0，说明语义判断对当前数据的使用不稳定。运行时语义评估输入现只携带当前
工具调用的名称、参数和结果，不再把完整事件轨迹冒充 `tool_results`；评估指令明确要求
逐项核对当前业务记录，并将旧私有值判为错误。本地测试验证输入结构和提示，真实模型
稳定性仍待下一次获准的 live 复测。

实验 runner 的最终 `score` 现采用硬门禁：构建、离线评分、live rollout、隐私审查、
奖励校准或容器清理任一阶段未通过时，交付分为 0；失败前计算出的高分保留在
`diagnostic_score`，离线分仍保留在 `offline_score`。这样 9.44 分但最终不合格的
样本不会再被误读为可交付 9.44 分。


### Unified training eligibility

Consume `status.json.training_ready` as the final boolean for using a sandbox
in training. Missing values in historical files mean **not certified**.
`success` and `status: success` continue to describe construction completion.
The builder always initializes `training_ready` to false, including when
`--skip-auto-score` is used. The experiment runner sets it to true only after
successful offline scoring, verified live execution, live reward calibration,
data governance and trajectory privacy checks, and final cleanup. Offline-only
runs remain false. A new attempt or failed final gate revokes readiness.
The final job result also carries `training_ready`.

This certifies environment eligibility under the pipeline gates, not measured
learning gains or production cohort certification.
