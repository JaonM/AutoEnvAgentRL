# V3 用户剧本复杂度提升设计

状态：已并入 `docs/v3-domain-world-design.md`（第 3 节），以该文为准。目标：让 V3 的模拟用户能演出 τ²-bench 那样复杂的剧本，训练 agent 应对各种真实情况；
同时保持奖励完全确定。

## 1. 现状与差距

| 维度 | τ²-bench | V3 现状 |
|---|---|---|
| 对话风格 | 逐条消息、不照搬剧本、逐步透露、不编造 | 基本一致 |
| 剧本复杂度 | airline 50 题中：带条件或备选 29 题，坚持诉求 20 题，记不清的信息 8 题，多诉求 8 题，涉及转人工 7 题（关键词粗略统计） | 只有处境、目标、已知信息和想被告知的事；用户有求必应，不改主意，不讨价还价 |
| 结束信号 | STOP / TRANSFER / OUT-OF-SCOPE | 只有"结束"一种 |
| 决定权 | 用户（大模型）按剧本决定是否同意 | 平台按规则决定是否同意（奖励确定） |

## 2. 设计原则

1. **决定结果的信息全部结构化**：凡是影响正确最终状态的内容（选哪个备选、同不同意某次写操作、最终改成什么），都写进
   `user_facts` 或审批规则，oracle 能读到，平台按规则执行。大模型只负责"怎么说"，不负责"决定什么"。
2. **剧本只影响对话过程**：说话顺序、什么时候透露、坚持几轮、什么时候改口，这些写进新增的 `user_script`，
   由用户模拟器演出，不影响判分。
3. **参考解必须能应对剧本**：结构化的剧本行为（记不清、先给错信息）由运行时模拟出来，codex 写的参考解必须能正确处理，
   否则沙箱通不过认证。这样保证每个剧本都有解。
4. **向后兼容**：没有 `user_script` 的任务行为不变，已有的两批沙箱继续可用。

## 3. 剧本要素（第一版 9 种）

| 要素 | 用户的表现 | 结构化表示（影响判分） | 运行时 / 认证如何保证 |
|---|---|---|---|
| **多诉求** | 一次通话提出 2–3 件事，可以一开始就说，也可以办完一件再提下一件 | 每件事的期望结果都在 oracle 里 | 参考解要办完所有诉求 |
| **备选方案** | "要 A；A 不行就要 B；B 也不行就算了" | 备选顺序作为事实；对各个方案的审批规则（同意 B、拒绝其他） | 首选在数据里设为不可行，参考解必须走到备选 |
| **记不清** | "订单号不记得了，用邮箱查行吗" | 标记部分事实为 `forgotten`，同时给出替代身份信息 | 运行时 `ask` 这些事实时返回"用户不记得"；业务工具要提供替代查询方式，参考解必须改用替代方式 |
| **先给错信息** | 先报一个错的编号，被告知查不到后再改正 | `wrong_first`：错误值和正确值 | 运行时第一次 `ask` 返回错误值，之后返回正确值；参考解必须能处理"查不到、再确认" |
| **坚持不合规诉求** | 先要政策不允许的结果（如额外赔偿），被拒后坚持 n 轮，再接受或要求转人工 | 正确结果是不执行这次写操作，或者执行转人工 | env 按规则拒绝不合规的写操作；判分看最终状态（没有违规写入） |
| **中途改主意** | 听到价格或条件后，改成另一种办理方式，或者取消 | 最终意图作为事实；对原方案的审批为"拒绝"，对新方案的审批为"同意" | 审批由平台按规则执行；参考解按最终意图办理 |
| **超出范围 / 转人工** | 提出政策之外的请求，或者主动要求转人工 | 环境提供转人工工具（视为一次写操作，记录状态） | 政策写明哪些情况必须转人工；判分看是否转了 |
| **含糊需求** | "帮我改一下那个订单"，而名下有多个订单 | 用户心里确定的那个订单作为事实 | 参考解必须先问清楚再办 |
| **性格与说话方式** | 着急、啰嗦、话少、注重细节、不太懂行、非母语表达 | 不影响判分 | 只影响模拟器的说话方式 |

## 4. 数据结构

`request.json` 新增可选的 `user_script`：

```json
"user_script": {
  "goals": ["exchange the keyboard", "then ask about the thermostat"],
  "fallbacks": [{"if": "no clicky full-size RGB keyboard", "then": "accept the version without backlight"}],
  "forgotten": ["email"],
  "wrong_first": {"order_id": "#W2378165"},
  "pushback": {"demand": "a $50 voucher for the delay", "rounds": 2, "then": "accept"},
  "change_of_mind": {"after": "hearing the change fee", "to": "cancel instead"},
  "traits": ["detail-oriented", "wants everything done in one go"]
}
```

运行时只读取其中会影响执行的 `forgotten` 和 `wrong_first`；其余字段只给用户模拟器。所有决定结果的值都在
`user_facts` 和审批规则里，`check_request` 负责检查两者一致：比如 `wrong_first` 的键必须是存在的事实，
`fallbacks` 必须有对应的审批事实。

## 5. 各组件的改动

| 组件 | 改动 | 是否在签名范围内 |
|---|---|---|
| 任务生成提示（REQUEST_AUTHOR） | 按分配的剧本要素写 `user_script`、对应的事实和审批，以及数据里的触发条件（首选不可行、多个同类订单等） | 否 |
| 生成计划 | 每个任务随机分配 1–3 种剧本要素，按比例控制（见第 6 节），写进 assignment.json | 否 |
| `check_request` | 检查剧本和事实、审批是否一致 | 否 |
| env 作者提示（AUTHOR） | 提供替代查询工具、转人工工具；参考解要处理记不清、先给错信息、备选方案 | 否 |
| 运行时 `Episode.ask` | 支持 `forgotten`（返回不记得）和 `wrong_first`（第一次返回错误值） | **是** |
| 用户模拟器 | 按 `user_script` 演出：多诉求的顺序、备选、坚持 n 轮、改主意、性格；新增 `[TRANSFER]` 信号 | **是** |
| 结构化用户（`v3_ask`） | 同样遵守 `forgotten` 和 `wrong_first` | **是** |
| 判分 | 不变 | — |

## 6. 剧本要素的比例（第一版）

每个任务分配 1–3 种要素。参照 τ²-bench airline 的分布：

| 要素 | 比例 |
|---|---|
| 备选方案 | 40% |
| 坚持不合规诉求 | 30% |
| 多诉求 | 30% |
| 记不清 | 20% |
| 含糊需求 | 20% |
| 先给错信息 | 15% |
| 中途改主意 | 15% |
| 超出范围 / 转人工 | 10% |
| 性格与说话方式 | 每个任务都有 |

## 7. 验证

1. **单元测试**：运行时的 `forgotten` / `wrong_first`，模拟器提示的拼装，`check_request` 的一致性检查。
2. **小批试点**（30 个任务）：看构建良品率、policy gate 通过率（deepseek 在复杂剧本下仍至少能解 1/4）、剧本执行情况。
3. **剧本执行检查**：抽样对话记录，用评审模型检查模拟器是否按剧本演出（坚持轮数、备选顺序、是否改口），只作诊断用。
4. **人工抽查**：和 τ²-bench 的对话记录并排对比风格和复杂度。

## 8. 对实验的影响与安排

- 运行时和用户模拟器在签名范围内，改完后，已经构建的沙箱需要重签一次。旧沙箱没有 `user_script`，行为不变。
- 建议：实现并通过试点后，第一、二批照旧构建完成（简单剧本），**第三批**用复杂剧本生成，训练时两类混合。
  如果试点效果明显更好，后续批次全部用复杂剧本。
- 预计工作量：实现约半天，试点约 4–6 小时（生成和构建）。
