# V3 方法有效性验证：Qwen3-0.6B 在 τ²-bench 与 BFCL-v3 上的提升

分支：`v3-bench-validation`（从 `main` 77348bf 建立）。

## 目的与假设

验证本项目方法能显著提升 Qwen3-0.6B 在两个外部 agent benchmark 上的成绩。本项目方法指：用 V3 生产线自动生成业务沙箱，用老师示范做 SFT 冷启动，再在沙箱里做 GRPO。

- H1：τ²-bench（零售、航空）上，SFT+RL 模型的 pass^1 比原始模型高至少 0.10（绝对值），且高于只做 SFT 的模型。
- H2：BFCL-v3 的多轮类别得分明显提升。
- H3：不损害通用能力。BFCL 的单轮非 live 类别下降不超过 2 个百分点。

## Benchmark 与指标

| benchmark | 用哪些部分 | 指标 | 说明 |
|---|---|---|---|
| τ²-bench | airline、retail；telecom 单独报告 | pass^1，每题 4 次取平均，另报 pass^4 | telecom 要求用户自己也操作设备，本项目没有这种交互模式 |
| BFCL-v3 | multi-turn（base、miss_func、miss_param、long_context）；single-turn 非 live 作回归对照 | 官方准确率 | 按状态和执行路径判分 |

站内参考成绩：τ²-bench 上 Qwen3.5-0.8B 为 0.116，Qwen3.5-2B 为 0.488；BFCL-v3 上 Qwen3 VL 4B Instruct 为 0.633。两个榜单都是自报成绩。

## 对比组

- A：原始 Qwen3-0.6B
- B：A + SFT（V3 沙箱上的 deepseek 示范：客服口吻，不带思考）
- C：B + GRPO（V3 沙箱，自由对话用户，随机平台工具名）
- 第二期（可选）：带推理的 SFT 加 think 模式的 RL

三组的设置完全相同：同一个评测工具、同样的解码参数（不带思考、温度按官方默认）、同一个 τ² 用户模拟器（deepseek-flash；官方默认是 gpt-4.1，这一点作为偏差注明）。

## 推理服务

两个评测工具都通过 OpenAI 兼容接口调用模型。我们自建一个本地服务，复用 rl `Policy` 的渲染与工具调用解析，保证 benchmark 看到的格式和训练时完全一致。不用 mlx_lm.server，因为它的工具调用格式和训练可能不同。

## 防污染

- 任何阶段都不使用 τ²-bench 或 BFCL 的数据和任务：示范、SFT、RL 都不接触。
- 生成训练沙箱时，屏蔽航空、机票、电信、手机套餐相关领域。
- 现有沙箱里有售后退换类任务，和 τ² retail 在领域上相近（没有数据重叠），所以 retail 单独报告。航空是最干净的迁移指标。

## 交互约定差异与对策

τ²-bench 里没有"提交答案"工具：agent 说完、用户结束对话就算完成。本项目训练时，交付靠调用提交工具。对策：

1. 训练数据中加入一部分"最后一句话就是交付"的任务（主观任务已经是这种形式，再扩大比例）；
2. 训练前后各跑一次 `heldout` 命名探针，统计调用不存在工具的比例；
3. 平台工具名每个 episode 随机，避免模型背下工具名。

## 规模

- 训练沙箱：用 `run_pipeline.sh` 扩充到 100–200 个（dev 划分，每批 30 个，parallel 3），加上已有的 34 个；
- 示范：每个沙箱 4–8 个 episode，合计 600–1500 条；
- SFT：0.6B 全参，学习率 1e-5，训练 1–1.5 个 epoch，按领域留出验证集做早停；
- RL：先用 SFT 模型测 pass@4，筛出成功率在 0 和 1 之间的任务再训练。

## 步骤

1. 安装两个评测工具，实现本地推理服务，测出 A 组的基线；同时跑 `heldout` 探针。
2. 扩充训练沙箱，采集示范（带口吻和推理）。
3. SFT 得到 B 组，在两个 benchmark 上评测。
4. RL 得到 C 组，在两个 benchmark 上评测。
5. 汇总：分领域、分类别的成绩，置信区间，失败案例分析；结论和数据追加到本文末尾。
