# V3 领域世界模式与用户剧本：完整设计方案

状态：设计稿，待评审。取代 `docs/user-script-design.md`，并吸收其中的内容。

## 0. 摘要

V3 现在是"一题一个小环境"：每个任务有自己的几张小表、1–4 个工具和一份只含相关规则的政策。真实业务不是这样的：
agent 面对的是一个**持续存在的系统**，有十几个工具、海量数据和一本完整的政策手册，每个客户只涉及其中一小部分；
客户本身也不总是配合的，会给出备选方案、讨价还价、记不清信息、中途改主意。

本方案为 V3 增加**领域世界模式**：每个领域构建一次大环境，在上面批量出题；每道题配一个**用户剧本**
（一棵确定的决策树，加一段自由演出的说明）。现有的一题一环境模式保留，两种模式并存。
奖励仍然完全确定，可信度仍然靠独立实现的差分认证来保证。

## 1. 目标与原则

### 目标

1. 训练数据接近真实业务：大环境、多工具、长政策、真实日期、长对话、复杂用户。
2. 奖励确定且可信：每个任务的期望结果由独立实现交叉验证。
3. 规模化成本更低：codex 只在构建领域世界时出手，出题由便宜的模型完成。

### 原则

| 原则 | 含义 |
|---|---|
| 平台通用 | 平台能力只能来自真实业务的普遍需求；不出现任何 benchmark 的工具名、数据结构或政策措辞 |
| 配置与平台分离 | 领域选择、任务比例属于实验配置；平台默认仍从知识图谱采样多样领域 |
| 决定结构化、说法自由 | 影响结果的用户决定写成结构化的决策树，由平台执行；措辞、语气、节奏由模拟器自由演出 |
| 独立实现、差分认证 | 环境、verifier、标准动作由不同会话分别产出，互相验证 |
| 两种模式并存 | 一题一环境模式继续用于独立任务（直接计算、单次查询、主观建议） |

**能力准入准则**：一项能力要加进平台，必须在真实业务中普遍存在，并且对评测 benchmark 以外的场景也有用。
例如"双方都要操作设备"只对应少数领域，本期不做。

## 2. 核心概念

```
领域世界 World（每个领域构建一次）
├─ schema           实体与关系（客户、账户、订单、预订、支付方式、商品或服务……）
├─ data generator   确定性的数据生成器（带种子），生成几百到几千条记录，包含边界情况
├─ clock            真实日期时间锚点（如 "2026-03-14 10:30, UTC+8"），规则按真实日期计算
├─ spec             完整的内部规格：所有业务流程的规则（判分依据）
├─ agent_policy     由 spec 改写的客服手册（agent 只看这份），并通过覆盖检查
├─ tools            12–20 个工具：身份核实查询、各类查询、写操作（参数可以是嵌套结构）；移交人工等只在领域政策规定时才有
└─ verifier           领域级 verifier：给定初始数据、用户事实、决策树和时间，计算任意任务的期望最终状态与答案

任务 Task（每个世界上批量生成）
├─ target           涉及的客户和记录（从世界数据中选取，必要时做少量定制修改）
├─ user_facts       只有用户知道的信息（身份信息、编号、偏好）
├─ decision_tree    用户的决定（结构化，由平台执行，verifier 也读取）
├─ script           自由演出的说明：诉求顺序、性格、坚持轮数、何时改口、记不清什么、先说错什么
├─ scene + opening  用户场景与开场白（沿用两阶段写法）
├─ gold_actions     每个决策分支各一组标准动作序列（由出题模型写，用于认证）
└─ expected         由领域 verifier 计算（不由出题模型写）
```

## 3. 用户剧本

### 3.1 决策树（结构化，决定结果）

决策树描述用户在每个决策点怎么选，条件只能引用**可客观判断的事实**：agent 提议的内容、当前数据库状态、用户事实。
用一种小型表达式语言写成 JSON，由平台解释执行，verifier 也读取同一份决策树来计算期望结果，不写成代码，便于审计。

```json
{"node": "proposal",
 "match": {"tool": "exchange_items", "args.new_item.switch": "clicky"},
 "decide": {"if": {"db": "product_variant_available", "args": {"switch": "clicky", "backlight": "rgb"}},
            "then": "approve", "else": "reject"}}
```

覆盖的决策类型有五种：同意或拒绝某次写操作；在多个方案中选择（按偏好顺序和可行性）；被拒后接受、继续坚持还是要求转人工；
听到费用或条件后改变意图；多诉求时决定是否继续办下一件。

### 3.2 剧本要素与比例（每个任务 1–3 种，另加性格）

| 要素 | 用户的表现 | 认证保证 | 比例 |
|---|---|---|---|
| 备选方案 | 要 A，A 不行就要 B | 数据里首选不可行；每个分支都有标准动作序列 | 40% |
| 坚持不合规诉求 | 先要政策不允许的结果，被拒后坚持 n 轮，再接受或要求转人工 | 期望结果是"不执行"或"转人工"；env 按规则拒绝违规写操作 | 30% |
| 多诉求 | 一次通话 2–3 件事，可以开头就说，也可以办完一件再提 | 期望结果覆盖全部诉求 | 30% |
| 记不清 | 不记得订单号或邮箱，能提供替代信息 | 运行时对这些事实返回"不记得"；世界里有替代查询工具 | 20% |
| 含糊需求 | "改一下那个订单"，而名下有多个订单 | 期望结果针对用户心里那一个；标准动作里包含先问清楚 | 20% |
| 先给错信息 | 先报错的编号，查不到后改正 | 运行时第一次返回错误值 | 15% |
| 中途改主意 | 听到费用后改成取消 | 由决策树表达 | 15% |
| 超出范围 | 提出这项业务根本不处理的要求（区别于政策明确禁止的"坚持不合规诉求"） | 期望结果不变；政策写明这类请求怎么答复（婉拒、指引去处，或该领域自己提供的移交方式） | 10% |
| 性格 | 着急、啰嗦、话少、注重细节、不太懂行、非母语表达 | 不影响判分 | 每个任务都有 |

### 3.3 用户模拟器

模拟器读取剧本的说明部分，以及平台告诉它的决定结论（同意或不同意、选了哪个、是否坚持），用自然语言演出。
结束信号沿用 `[END]`（办完或不想继续）；剧本覆盖不到的情况按"拒绝"处理并记录。转人工不作为平台概念，只在领域政策规定时作为该领域的工具出现。
坚持的轮数由平台计数，到了约定轮数就告诉模拟器"现在接受"或"现在要求转人工"，不依赖大模型自己数。

## 4. 生成流水线

### 4.1 世界构建（每个领域一次，使用 codex）

| 步骤 | 产出 | 由谁完成 |
|---|---|---|
| W1 领域 | 领域名称与说明（知识图谱采样，或配置文件指定） | 现有流程 |
| W2 世界规格 | schema、业务流程清单（8–15 个）、完整 spec、工具清单、时间锚点 | codex 规格会话 |
| W3 数据生成器 | 确定性生成器，产出几百到几千条记录，包含边界情况和干扰项 | codex 数据会话 |
| W4a 环境 | 全部工具的实现 | codex 作者会话 |
| W4b verifier | 领域级 verifier（看不到环境实现） | codex verifier 会话 |
| W5 政策 | 对外政策改写与覆盖检查（沿用现有流程） | deepseek |

### 4.2 世界认证

1. **静态检查**：工具定义、参数类型、不得出现通用读表工具、身份核实流程完备。
2. **流程探针**：codex 规格会话为每个业务流程给出 3–5 个探针场景（典型、边界、拒绝），env 执行标准动作，
   与 verifier 的期望结果做差分比对，有分歧时按 spec 原文仲裁（沿用现有仲裁机制）。
3. **换种子复验**：用不同的种子重新生成数据，探针差分依然成立（防止实现依赖特定数据）。

世界认证通过后，才在它上面出题。

### 4.3 出题（每个世界批量生成，使用便宜的模型）

| 步骤 | 内容 |
|---|---|
| T1 选题 | 按配额抽取业务流程和剧本要素；从世界数据中查询合适的目标客户和记录（出题模型通过只读查询工具访问数据） |
| T2 定制 | 必要时对目标记录做少量修改，制造触发条件（比如让首选商品缺货） |
| T3 剧本 | 写 user_facts、决策树、剧本说明、用户场景 |
| T4 标准动作 | 为每个决策分支写一组标准动作序列 |
| T5 开场白 | 沿用两阶段写法：开场白写手只看场景和性格 |

### 4.4 任务认证（每道题）

1. **一致性检查**：决策树只引用存在的事实和数据；剧本要素齐全；每个分支都有标准动作。
2. **差分**：在 env 中重放每个分支的标准动作（平台按决策树发放授权），得到的最终状态必须等于 verifier 对该分支的期望结果。
3. **反例**：什么都不做、违规写入、用旧数据作答，都必须拿不到分（沿用现有的反例 gate）。
4. **难度下限**：标准动作的工具调用次数达到下限（按任务形态设定）。
5. **抽取探针**：答案能从客服说法里完整读回（沿用现有探针）。
6. **policy gate**：deepseek 在自由对话、复杂剧本下至少解出 1/4。
7. **剧本执行诊断**（不作门槛）：抽样检查模拟器是否按剧本演出（坚持轮数、备选顺序、改口时机）。

### 4.5 奖励可信度的补充措施（已实现）

| 措施 | 做法 | 位置 | 是否在签名范围内 |
|---|---|---|---|
| ~~第三个 verifier~~ | 已移除（2026-10-14）：按同一份规格写，重复的是同一种理解，防不了系统性误读；改由按流程审计和逐条规则审计覆盖相关错误 | — | — |
| 手册充分性 | 把 agent 手册、用户全部事实、参考解查到的数据都给模型，要求它推断写操作和答案；k 次都推不对就淘汰（stage `sufficiency`），推不对的字段记为手册缺口 | `certify/sufficiency.py` | 否 |
| 允许多种正确结果 | 规则明确允许自由选择、事实又没定下来时，verifier 在 `alternatives` 里列出其他正确结果（最多 3 个，不能重复，主结果有写操作时不能是"什么都不做"）；判分取最好的一个，`outcome` 记录命中哪个；仲裁者遇到这种分歧时补 alternatives | `core/reward.py`、`certify/gates.py`、`checks.py`、提示 VERIFIER / ARBITER | 是 |
| 模拟器透露审计 | 自由对话失败的回合，由评审模型检查模拟用户是否漏说、说错、编造或与平台决定相反；每条错误必须逐字引用用户原话（并指明事实键），否则丢弃。有错误的回合标为无效：奖励不变，但训练时不参与 GRPO 的组基线、也不产生梯度。`SIMULATOR_AUDIT=off` 可关闭 | `core/disclosure.py`、`serving/server.py`、`rl/environments/v3.py`、`rl/data/trajectory.py` | 是 |
| 分歧挖掘 | 读 policy gate 的结果：同一世界上 ≥2 个失败回合以相同的写操作和答案结束（收敛失败），或评审判为 `reference_suspect` / `policy_gap` 的任务被标记；`make_split.py --exclude` 可把它们排除出训练 | `production/disagreement.py` | 否 |

世界模式保留独立实现的 env 与 verifier，不再生成第三个 verifier；任务另做目标敏感性与手册充分性检查。

## 5. 运行时

| 方面 | 设计 |
|---|---|
| 数据 | 世界的数据库在内存中加载一次，每个 episode 用写时复制的快照；任务的定制修改叠加在快照上 |
| 时间 | system 中给出真实日期时间；规则按真实日期计算 |
| 授权 | `approval_key` 推广为决策树解释器：输入提议、当前数据库和用户事实，输出决定 |
| 记不清 / 说错 | 运行时按剧本处理 `ask`：`forgotten` 返回不记得，`wrong_first` 第一次返回错误值；自由对话下模拟器同样遵守 |
| 超出范围 | 不需要平台机制：期望结果不变；领域若规定移交，由领域工具实现 |
| 判分 | 不变：最终状态，加上答案（记录的或从话里抽取的）；主观任务用 rubric |
| agent 看到的内容 | 完整的对外政策、12–20 个工具（名字随机化不变）、开场白 |

## 6. 训练与评测

- **训练接入**：tasks.json 增加 `(world, task)` 类型的条目；rl 适配器加载世界包和任务；两种模式可以混合训练。
- **训练参数**：步数上限调到 40–60，上下文 24–32k，对齐真实对话长度。
- **评测（同时用来检查过拟合）**：
  1. τ²-bench（airline、retail）；
  2. V3 留出领域世界（领域完全没见过）；
  3. BFCL 多轮；
  4. 再选一个风格不同的 benchmark（如 VITA-Bench）。

  如果只有 τ²-bench 提升、其余不动，视为过拟合。
- **对比实验**：C_task（现有的一题一环境训练池）、C_world（领域世界）、C_mix（两者混合），回答"领域世界是否更有效、是否泛化"。

## 8. 里程碑

| 阶段 | 内容 | 预计 |
|---|---|---|
| M1 剧本（一题一环境模式内） | 决策树解释器、剧本字段、forgotten / wrong_first、模拟器演出、转人工；30 题试点 | 1 天 |
| M2 世界构建与认证 | 世界规格、数据生成器、领域 verifier、流程探针、换种子复验；构建 3 个试点世界 | 1–1.5 天 |

## 9. 风险

| 风险 | 对策 |
|---|---|
| 世界环境大，出错的地方多，一个 bug 影响整个领域的所有题 | 流程探针、换种子复验、每道题的分支差分三道防线；世界认证不过就不出题 |
| 出题模型写的标准动作有误 | 必须与 verifier 的期望结果一致才算通过，否则淘汰该题 |
| 决策树表达能力不够 | 第一版覆盖五类决策；遇到表达不了的情况，记录下来后扩展，不退回到让大模型自由决定 |
| 长政策、多工具超出 0.6B 的能力 | 按难度分级（工具数、政策长度、剧本要素数），做课程式训练 |
| 过拟合 benchmark | 第 1 节的准入准则，加第 6 节的多 benchmark 评测 |
| 模拟器不按剧本演出 | 坚持轮数等关键节点由平台计数并提示；剧本执行诊断持续监控 |

## 10. SOP 蓝图与依赖图：2026-10-19 实现

当前零售、航空采用 `sop-v1`：先声明业务对象和完整事务，再按业务意图组合流程；多目标补题不再任意枚举写操作的排列组合。

### 规格与执行边界

- `sop_blueprint.objects` 描述对象身份、生命周期和范围。订单/预订的付款流水、用户保存的资金方式等仍是嵌套业务记录，未虚构外部支付服务。
- `atoms` 是查询或完整的业务事务适配器：公共工具、输入/输出 JSON Schema、规则来源、后端前提、agent 义务、读写范围、效果、原子失败回滚、重试语义和金额单位。业务前提文本不等于形式化证明：具体语义由独立验收案例、差分 verifier 和真实任务回放共同检查。
- `methods` 声明业务意图、流程列表、共享对象约束和 `data/state/resource/authorization` 边。资源共享导致的必要顺序与真正的因果依赖分开记载。
- `sop_contract.cases` 在独立合成数据上执行有向无环图：节点参数能引用实际前序输出，支持条件分支；每次成功操作必须有独立断言。失败回滚、未声明字段写入和越过对象范围的修改都会拒绝验收。
- 图拒绝循环、未知原子操作、没有数据边的结果引用、未排序的读写冲突。独立节点采用正反两种拓扑选择顺序复验。第一版最多 64 节点；未实现任意循环、通用搜索规划器或自动跨事务补偿。
- 事务验收使用受控授权，授权安全仍由既有 consent/negative/policy 检查负责。授权边不会虚构新的业务身份接口。

通用实现位于 `src/env_factory/sop.py`。它没有零售、航空或其他行业分支。领域规则位于 `experiments/world_extensions/sop_specs.py`，首批零售 4 个、航空 7 个组合方法，所有方法都有确定性执行见证；这不是对全部业务 SOP 或全部 benchmark 任务的穷举覆盖。

### 新世界、新题与自动修复

新领域可在配置中启用 `sop_required: true`，由规格作者先生成蓝图及独立验收案例；缺少蓝图会在实现前拒绝。也可由调用方直接提供 `sop_blueprint/sop_contract`。平台在进入 env/verifier 实现阶段前计算契约哈希。原有未启用 SOP 的领域保留兼容路径。

`sop` 已加入标准认证和失败反馈。环境缺陷进入已有有界自动修复；修复者不能修改 request、独立 verifier 或验收真值。若只是出题者声明了并不存在的依赖，反馈给任务作者修题，不能靠修改沙箱让题成立。图书馆夹具验证同一机制可以自动修复第三个领域。

新多目标题必须选择已声明的 `sop_method`；检查流程顺序、同一对象、预期分支及结果绑定。标为因果的状态边会移除前驱并比较后继结果/写入效果，独立的两项业务不能仅靠保留前一步修改冒充因果关系。数据边同时检查绑定移除是否改变后继结果。独立工作可以用明确的无因果声明表达，但不会自动算作依赖复杂度。

航空支持 `goal.bindings`，例如后一个预订的 `payment_id` 使用前一个赔偿结果的 `certificate_id`；参数位置先填 null，运行时填实际值。共享函数只解析引用，不共享业务计算。用户模拟器只看到“使用前一步实际结果”的意图，不接收绑定表达式；SOP 图、验收案例和 oracle 均不进入学生消息。

任务验收另外按真实参考参数回放工具调用并检查写入范围。学生评分仍依据允许的最终业务状态、回答及政策合规性，不要求复现图的某一条标准工具轨迹。

### 多样性、版本与实验

结构去重包含规范化 SOP 图、结果绑定和分支，继续结合业务政策上下文与交互障碍；姓名、编号、金额替换不构成新结构。发布时重查依赖证据，并输出 `sop_coverage.json`，区分历史回放与新 SOP 组合。覆盖目标不等于已经采样成功。

`output/world_sop_v1` 的全量、训练、开发共 6 个世界均已验收。零售 30 个行为案例，航空 24 个；转换为 SOP 图并增加并行读取案例后共 57 个独立案例图。既有数据规模、私有实体划分、公共政策和 tau2 评分器未改动。

旧队列的 556 条已验收示范先在新版本逐条重认证、原样回放；只有对话、工具观察、公开政策和判分一致才复用，并保留 `deterministic_replay` 来源。新题使用新的沙箱与 SOP 出题规则。

`experiments/bench/advance_sop_sft.py` 等待迁移完成，准备缺口、冻结运行副本，启动采样与训练续跑；发生迁移错误会停止并记原因。所有 DeepSeek 调用沿用 `ENVFACTORY_OFFPEAK=1` 传输门禁：北京时间工作日 09–12、14–18 为项目配置的高峰窗口。补齐 1000 train / 200 dev 并通过联合发布后，自动接续既定 seed0/seed1、公开 agent 数据等比例混合、开发集早停、164 题及固定 32×8 评测。

## 11. 规格与数据分离：2026-10-19

新产物的 `request.json` 保留业务规则、公开政策/API、goal schema、SOP 蓝图、数据约束及来源；不再内嵌完整业务记录、用户事实和验收夹具。`request_assets`（version 1）按字段引用同目录文件并保存 SHA-256：`tables → data.json`、`user_facts → facts.json`、`behavior_contract → behavior_contract.json`、`sop_contract → sop_contract.json`。后两者是独立验收依据，外置不会削弱检查，也不会交给学生。SOP 原子事务和组合方法仍在规格里。

`core.spec.read(path)` 解析引用并还原原始字典，不增加默认字段；`load(path)` 在此基础上补默认值、执行规格校验。旧的全内嵌格式继续可读。路径必须留在请求目录内；缺文件、哈希不符、同一字段同时内嵌与引用均拒绝。`spec.write(request, path)` 接收已经解析的字典，统一写入数据文件和引用。非标准文件名（例如 `requests/gen-000.json`、`world.json`）使用各自的 `gen-000.assets/`、`world.assets/` 子目录，避免批量枚举 `*.json` 时把数据误当任务，也避免多个请求互相覆盖数据。

生成会话默认从 `brief.md`、规格、`data_preview.json` 和答案 schema 开始。预览提供每表行数、顶层字段和经过明确标记的受限样例（每表最多一条、样例不超过 4096 字节）；它不是完整 schema 或运行数据。需要嵌套字段或特定客户记录时，用 Python 精确读取，避免打印整个数据集。宿主程序仍用完整数据执行所有工具、扰动、验收和评分。任务作者继续只获得原来的 owner shard 和外键闭包，分离存储不扩大可见范围。

生成、世界构建、任务组装、bundle 导出/加载/重新认证、实验补题/回放和数据筛选入口统一处理该格式。Bundle manifest 覆盖全部被引用文件；重新认证保留这些哈希。任务作者及实现修复者不能修改引用数据或独立案例。当前改造没有按原子事务分模块生成代码，也没有引入自动上下文检索器；按需读取仍由生成会话执行。

对旧规格做独立无损转换：

```bash
.venv/bin/python -m env_factory split-request \
  --request path/to/old/request.json --output path/to/new_directory
```

输出目录必须不存在；转换不覆盖原世界，也不直接重签原 bundle。`output/world_spec_split_v1` 保留当前零售、航空的转换与验收证据：完整字典逐字段相等，零售 `request.json` 从 3,012,223 字节降至 136,596 字节，航空从 7,171,877 字节降至 151,495 字节。预览分别为 4,338 / 4,722 字节。这是文件体积变化，不是实测模型 token 或费用节省比例。完整业务数据未删减，独立新 bundle 经过原有业务认证。

正在运行的 `world_sft_sop_v2/runtime` 与其世界不改动，继续原实验；新代码影响后续构建。加载旧 bundle 时仍遵守 platform identity 校验，需在新平台完整重新认证，不能仅修改签名绕过验收。


## 业务状态机与事件调度

需要真实模拟物流、验收、支付等后续动作的世界，使用可选的 `lifecycle_schema`、题目 `scenario` 和独立 `lifecycle_contract`。世界定义规则，题目选择合法初始历史和完成范围，episode 维护私有事件队列；聊天声明不会改变业务状态。详见 [状态机方案与实现](lifecycle-state-machine.md)。
