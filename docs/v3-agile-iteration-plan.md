# V3 小步快跑实验迭代计划（τ²-bench，Qwen3-0.6B）

状态：2026-10-13 制定，取代 `v3-benchmark-validation-plan.md` 中的执行顺序（预注册的评测口径与 H1 不变，期望值见第 1 节的校准）。

## 0. 原则

1. **每轮只改一个变量**，改完立刻快评；有提升才进入下一轮，没提升先诊断，**最多做一轮修复**，仍无提升就重新规划，不继续往流水线上加功能。
2. **GPU 主线与工程支线并行**：GPU 只跑训练和快评；codex/deepseek 生成、工具测试、判分修复在支线做，支线成果只在两轮迭代之间并入。
3. **运行时改动集中合并**：签名范围内的改动只在两轮之间合并，合并后统一重签所有沙箱，构建或评测进行中不改。
4. **只看我们自己的开发集做诊断和定向生成**，τ²-bench 只用来打分，不用来出题，避免过拟合 benchmark。

## 1. 评测口径

| 项目 | 快评（每轮必做） | 里程碑全评（I2、I3、I5 之后） |
|---|---|---|
| 范围 | airline 50 + retail 114，1 轮，seed 300 | 同样的题，4 轮（`eval_arm.sh`） |
| 耗时 | 不开 think 约 19 分钟；开 think 时，原始模型约 60 分钟（平均 430 个 token），训练后推理变短，预计约 30 分钟。长上下文解码受 KV 读取带宽限制，批量解码只带来约 1.5 倍提速 | 约 1–1.5 小时 |
| 服务 | `serve_openai.py`，对话前缀缓存（输出与不用缓存时逐字一致） | 同左 |
| 评审 | retail 的 NL 断言由 `LLM_*`（deepseek）评审，所有组相同（`tau2_run.py`） | 同左 |
| 判定 | 与上一轮按题配对：提升 ≥ 5 个点且配对检验 p < 0.1，记为"有信号" | H1：配对检验 p < 0.05 |
| 记录 | pass^1（总体、分领域、需写入/不需写入）和失败类型分布：没写入、无授权写入、答案错、轮数耗尽、提前结束 | 同左，外加 pass^k |

**期望值校准**（来自文献）：4B 模型在 τ² 上的提升普遍只有 5–7 个点（AWM 15.8→22.6，EnvFactory 25.3→30.1），1.7B 做完 RL 甚至可能下降。0.6B 的现实目标是**累计提升 5–10 个点**，主要来自 SFT；RL 视为加分项。原 H1 要求提升 0.10，作为最好情况保留。

旧基线 A（0.154）中，retail 有 33% 的回合因评审不可用而记零分，**作废**；以 I0 的新基线为准。

## 2. 主线迭代

| 轮 | 只改这一项 | 输入 | 产出 / 判定 | 预计耗时 |
|---|---|---|---|---|
| **I0 基线与设施**（进行中） | — | 原始 0.6B | 快评 A（不开 think）和 A-think；合并 `v3-reward-trust` 分支并重签所有沙箱 | 约 1.5 小时 |
| **I1 think 蒸馏** | SFT 带推理 vs 不带推理（同一批示范） | 现有 39 个沙箱（第一批 13 个、剧本试点 26 个），deepseek 示范，保留推理（单轮上限约 1500 字），按 agent 片段切样本 | 两个模型各快评一次，选出模式。数据少，**预期信号弱**；本轮主要验证 think 的流程和方向 | 约 4 小时 |
| **I1b 交错思考** | 多轮保留历史推理 vs 按模板丢弃（E9） | I1 选定 think 时才做，同一批示范 | 快评，选出推理保留方式 | 约 2 小时 |
| **I1c 推理预算** | SFT 加预算档位标注（E12） vs 不加 | I1/I1b 选定的配置 | 在两个预算（256、1024）下各快评一次，看"准确率–推理 token"曲线 | 约 3 小时 |
| **I2 环境数量** | 训练环境从 39 扩到 ≥100（采用 I1 选定的模式） | 第一、二批恢复构建，新增工具模糊测试（E1） | 快评 + **里程碑全评**。回答"环境数量的收益"（文献：少于 20 个时无效，100–500 个时持续提升） | 构建 1 天（机器），训练和评测 2 小时 |
| **I3 RL** | 在 I2 的 checkpoint 上做 GRPO | 经 pass@4 筛选、成功率居中的任务；模拟器审计屏蔽、环境级标准差归一化、动态采样 | 快评 + **里程碑全评** | 训练 2–3 小时 |
| **I4 复杂剧本** | 训练数据加入复杂剧本题 | 剧本试点通过的 12 题，再补生成到 50 题以上；开场白加入隐含意图改写（E6） | 快评：和 I3 比，剧本有没有用 | 生成半天，训练加评测 3 小时 |
| **I5 世界题** | 训练数据加入世界题 | 判分修复（E3）后重新认证的世界题；按调用链出题（E4） | 快评 + **里程碑全评** | 修复 1 天，训练加评测 3 小时 |
| **I6 定向补题** | 按**我们自己开发集**上的失败类型定向生成 | 诊断报告 → 定向生成环境和任务 | 快评 | 1 天 |

每轮训练从上一轮的最好模型继续，或者从头用累计数据训练（每轮开始前定好，同一组对比内保持一致）。

签名范围内的改动（E0、E3）分别在 I0 和 I5 开始前合并、统一重签。

E5 的细节沿用 AWM：每一层先检查，失败带报错重试，最多 5 次；非奖励环节允许约 10% 的出错率。E3 的"代码判分 + 评审第二意见"先在世界题上验证，有效再推广到所有任务。

**明确不采纳**
- 用 LLM 模拟环境本身（GenEnv 一类）：状态会幻觉、成本高。保持可执行环境加差分认证。
- 用纯 LLM 评审替代代码判分：AWM 的 ablation 显示纯 LLM 评审最差。评审只做失败回合的第二意见。
- 用 APIGen-MT-5k 等公开数据做 SFT：它基于 τ-bench 的环境生成，会污染 τ² 评测。
- 逐轮奖励：UserRL 显示整局奖励更好，保持终局奖励。

## 4. 没有提升时的诊断顺序

1. 先看失败类型分布有没有按预期变化（例如 SFT 之后"没写入"是否减少）。分布没变，说明问题在训练数据或格式；分布变了但分数没变，说明问题在判分或评测口径。
2. 抽 10 条失败的对话，与 teacher 在我们环境里的成功轨迹并排比较。
3. 检查训练和评测是否一致：模板、think 设置、工具名随机化、system prompt 语言。
4. 只允许一轮针对性修复；仍无提升，就带着证据重新规划。
