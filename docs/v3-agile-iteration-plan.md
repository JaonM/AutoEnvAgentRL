# V3 小步快跑实验迭代计划（τ²-bench，Qwen3-0.6B）

状态：2026-10-13 制定。2026-10-14 晚第三版：汇总探路 SFT（A、B 两组）的结果和"一口气全查"习惯的根因分析，并纳入四块内容：工具真实感、按形态出题（新增 single_write）、世界模式的奖励可信、RL 的功劳分配（反向课程、树状 rollout）。SFT 和 RL 统一不开 think。

## 0. 原则

1. **每轮只改一个变量**，改完立刻快评。有提升才进入下一轮；没提升先诊断，**最多做一轮修复**，仍无提升就带着证据重新规划。
2. **不只看分数，也看行为**：每轮同时报告 pass^1 和行为指标（第 1 节）。分数持平但行为指标变好，记为方向正确；分数涨但行为变坏，不采纳。
3. **治根不治标**：发现坏习惯先查它从哪来（数据、环境、判分），不直接加规则压制。例如不限制并行调用数，而是查出"一口气全查"的来源再修。
4. **GPU 主线与工程支线并行**：GPU 只跑训练和快评；生成、测试、判分修复在支线做，成果只在两轮迭代之间并入。
5. **改平台身份的改动集中合并**：`runtime`、`core/`、`serving/`、`certify/`（除 policy gate）的改动只在批量构建空闲时合并，合并后统一 `verify --resign`。提示词、生产线、实验脚本不在此列，可以随时合并。
6. **τ²-bench 只用来打分，不用来出题**；诊断和定向生成只看我们自己的开发集。
7. **控制随机波动**（2026-10-15 起）：同一份 A 数据训练三次，开发集平均奖励 0.274 / 0.345 / 0.292，单轮多调用 29% / 14% / 8%。因此每组至少 2 个种子、取平均；开发集检查报告置信区间；开发集 0.1 以内的差异不作结论；新组上线前先核对样本数和 token 数与预期一致（arm B 的近似成功样本被训练脚本静默丢弃，就是靠这一点才发现的）。

| 项目 | 快评（每轮必做） | 里程碑全评 |

**行为指标**（每轮必报）：
- τ² 上：`experiments/v3/bench/call_habits.py`，统计以下几项：
  - 错误过多中止局数；
  - 单轮超过 3 个调用的局占比；
  - 失败后重复调用的比例；
  - 编号无来源率；
  - 照抄示例值率。
- 开发集上：`dev_check.py`，统计以下几项：
  - 成功率和平均奖励；
  - 重复失败调用、调用不存在的工具、撞步数上限；
  - 先问后查的比例；
  - 单轮超过 3 个调用、编号无来源、照抄示例值的比例。

**基线 qA3（原始模型，不开 think）**：0.140（airline 0.34，retail 0.053，需写入 0.022，不需写入 0.667）。行为：错误过多 4 局，照抄示例值 29.5%，编号无来源 55%，失败后重复 24%。

**期望值**：0.6B 的现实目标是累计提升 5–10 个点。

## 2. 到目前为止的结论

| 实验 | 结果 | 结论 |
|---|---|---|
| T0 | 不开 think 优于开 think | 统一不开 think |
| I1/B1（25 个任务 SFT） | τ² 0.000 | 小数据 SFT 有害：编造编号、原样重试、调用不存在的工具 |
| I2p-A（506 局、129 个任务，LoRA r64，整局渲染） | 纯 SFT 0.134；插值 α=0.5 时 0.159（最好），0.3 和 0.7 时更低；都不显著 | 没崩，也没提升。需写入的题略升；不需写入的题下降；错误过多从 4 局升到 15 局 |
| I2p-B（A + 57 局近似成功） | 0.146（需写入 0.045，目前最好）；开发集 62% 的局撞步数上限、重复失败 14% | 近似成功样本带来了更长、更绕的对话，暂不采纳，待查原因 |

**"一口气全查"的根因**（I2p-A）：
1. 教师一拿到编号，就把相关查询工具全查一遍：46% 的调用出现在单轮 3 个以上调用的回复里，34% 的查询结果后来没用上。我们的环境工具少、效率分宽松，这样做没有代价。
2. 0.6B 只学到了"批量发调用"的形式，没学到"手里有编号才查"的前提。没有编号时，它就照抄 τ² 工具说明里的示例值，比如 `#W0000000`。
3. 506 局里只有 36 局出现过失败调用，没有一次是"编号不存在"，所以模型从没见过失败后该怎么改正，只会原样重试。

### RL 基础设施（R 系列）

| 编号 | 内容 | 平台身份 | 状态 |
|---|---|---|---|
| R1 | **精确分叉和恢复**。`POST /fork` 在服务进程内深拷贝整个 episode（数据库、对话、模拟用户的消息记录、同意凭证、步数和时钟），不重放、不调用大模型。`POST /restore` 从录制好的对话重建状态，用户回复直接取原文。现有的 `snapshot()/restore()` 靠重放动作，模拟用户会重新生成回复，所以不精确，也没有被训练流程调用过。验收：分叉后执行相同动作，工具返回和数据库完全一致 | **是**（`serving/server.py`） | ⏳ 先在分支上做 |

| R3 | **按文献修订**（VinePPO、SPO、TreeRL、Tree-GRPO、GiGPO、ARPO）：①分叉粒度定为 agent 的完整一轮（Tree-GRPO：按 token 或句子分叉 22.2，按 agent 步 36.8，链式 GRPO 31.8）；②优势 = 全局项 + 局部项，**两项都保留**：全局项 V(s) − V(开局) 或整局组优势，局部项 V(s) − V(父节点) 或兄弟续写间的相对优势（TreeRL 去掉局部项 −1.3；Tree-GRPO 预算小时只用树内项会崩溃，树间项是兜底基线；GiGPO 用 A_整局 + 1·A_步级）；默认直接相加（权重 1），不再取 0.5/0.5；③标准差归一化可省略或用任务级尺度（SPO、GiGPO 都发现不除以标准差持平或略好，难题上更好）；④只用非零优势的节点训练（SPO-tree）；⑤分叉点按熵选：每次工具返回后生成的前 k 个 token 的熵，相对开局熵的增量越大越先分叉（ARPO），辅以写操作前、用户拒绝后等规则点；⑥预算按主干和分叉约 1:1 分配（ARPO：16 条里 8 条整局采样最好，全部整局采样时明显下降），起步配置改为 8 条主干 + 4 个分叉点 × 2 条续写；⑦每个分叉点续写 2–4 条即可（SPO：二值奖励下 4–9 个蒙特卡洛样本足够，宽度 4/6/8 同等时长下效果相近）；⑧共享前缀只训练一次（续写的前缀只作上下文、不计 loss），等价于 ARPO 的软设定，不需要 TreeRL 的 1/√叶子数 重加权；⑨价值用蒙特卡洛估计、不训练价值网络（VinePPO：价值网络几乎不比随机基线好，蒙特卡洛估计更快达到更高精度）。另记：小模型和多轮任务收益最大（Tree-GRPO：3B 以下多跳任务 +16%–69%，单跳任务收益接近 0），与我们 0.6B + 多轮客服的场景吻合。后续可试 GiGPO 式的零成本步级分组：把"数据库状态 + 已透露事实 + 同意状态"相同的步骤视为同一锚点状态，不额外采样 | 否 | ⏳ |

## 6. 没有提升时的诊断顺序

1. 看行为指标和失败类型分布有没有按预期变化：没变，问题在数据或格式；变了但分数没变，问题在判分或评测口径。
2. 抽 10 条失败对话，和教师在我们环境里的成功轨迹并排比较。
3. 查训练和评测是否一致：模板、不开 think、工具名随机化、system 版式、工具说明里的示例值。
4. 只允许一轮针对性修复；仍无提升，就带着证据重新规划。
